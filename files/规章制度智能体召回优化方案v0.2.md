# 公司规章制度智能体 —— 召回优化方案

---

## 摘要

现有规章制度智能体采用一次性向量检索（RAG），召回准确率无法满足业务要求。

本方案的核心改动是：**把"一次性检索定生死"改成"先定位、再下钻、后确认"**——离线把制度库编译成带层级的知识目录，在线由大模型沿目录逐级收敛，每一步都通过工具调用取回条款原文，最后基于原文作答并引用条款编号。

配套必须做的一件事是**建立评测集**。没有它，任何优化都无法判断是变好还是变坏。

---

## 一、背景

### 1.1 业务场景

公司内部规章制度智能体，面向全体员工，承担制度类咨询的检索与解答，覆盖员工手册、考勤、休假、报销、奖惩、保密等制度内容。

`【待确认】：当前使用人数、日均提问量、覆盖的制度文件数量与总字数`

### 1.2 为什么"召回准确"是这类系统的生命线

规章制度问答和一般知识问答有本质区别，这决定了技术选型的方向：

- **答案必须是原文，不能是复述。** 制度条款涉及权利义务、金额、期限，任何同义改写都可能改变法律含义。
- **答错的代价不对称。** 闲聊答错是体验问题；制度答错会让员工算错年假、错过申诉期、报错金额，直接产生劳资纠纷风险。
- **结论要可追溯、可举证。** 员工会拿着机器人的回答去找 HR 对质。答案必须能一步点回到"某制度第 X 条"。

一句话：**制度检索的本质不是"找相似文本"，而是"精确定位条款"。** 这个判断贯穿本方案的所有设计。

## 二、遇到的问题

### 2.1 现象

`【待确认】：召回成功率的具体口径与数值。例如：在 XX 条测试问题中，top-5 命中正确条款的比例为 XX%`

当前状态是"体感很差"，但**缺少可量化的基线**。这是本方案要解决的第一个问题，也是做任何优化之前的前置条件。

### 2.2 把"召回差"拆开看

"召回成功率差"是一个笼统描述，它背后至少混着六种性质不同的失败。**它们的解法完全不同**，如果混在一起处理，就会出现"改了一处、坏了一处"的反复。

| 失败类型 | 典型表现 | 根因 |
|---|---|---|
| 结构破坏 | 条款被从中间切断，前件与后件分离 | 按固定长度切分，无视条款边界 |
| 术语鸿沟 | 用户问"请假"，文档写"休假管理"；用户问"年假"，文档写"带薪年休假" | 口语表达与制度书面语之间无桥梁 |
| 精确匹配失败 | 找"第 12 条""报销上限 5000 元"时检索不到 | 向量检索对编号、数字、专有名词表征能力弱 |
| 跨条款依赖 | "我这种情况怎么办"需要拼 3 条以上条款 | 单次检索只返回孤立片段 |
| 版本时效混杂 | 检索到已废止的旧制度 | 缺少生效/废止日期的元数据与过滤 |
| 干扰项淹没 | 库变大后，正确条款被大量相似条款挤下去 | 缺失精排环节 |

**关键认知：必须先做分桶统计，搞清楚上面六类各自占多少。** 经验上，前两类（结构破坏 + 术语鸿沟）通常占大头，而它们的修复成本远低于改造整个检索架构。

### 2.3 一个更前置的问题：没有评测

当前无法回答这样一个问题：**"这次改动之后，系统是变好了还是变坏了？"**

没有评测集，所有的方案讨论都只能停留在"我觉得这样更好"。这是本方案把"建评测集"放在第一阶段的唯一原因。

## 三、当前方案与局限

### 3.1 当前架构

`【待确认】：以下为典型 RAG 实现，请按实际情况修正`

```
制度文档（PDF/Word）
    → 文本抽取
    → 按固定长度切分（如 512 字）
    → embedding 模型编码
    → 向量库存储
                    ↓（查询时）
用户提问 → 编码为查询向量 → 向量库 top-k 相似检索 → 拼接 prompt → 大模型生成回答
```

`【待确认】：embedding 模型、向量库产品、切分参数、top-k 取值、是否已有 rerank`

### 3.2 这套流程在制度场景的失效点

逐条对应 2.2 的六类问题：

1. **切分阶段就丢了结构。** 固定长度切分会把"第十二条"从中间截断，条款的适用条件留在第 N 块、处理结果落在第 N+1 块。检索到任何一块都是残缺的，模型再强也拼不出来。
2. **检索阶段只有"语义相似"一个信号。** 用户问"第 12 条"，向量空间里"12"这个数字的表征极弱，反而"第 13 条""第 15 条"因为文本高度相似而排在前面。
3. **口语化的提问和书面化的制度之间没有对齐。** 用户的词汇和制度的词汇是两套体系，靠 embedding 的语义泛化能力去跨越这个鸿沟，效果不稳定。
4. **单轮检索无法处理需要推理的查询。** "我老婆生孩子我能休几天"需要先判断适用哪条制度、再定位具体条款，这是多步推理，不是一次相似度计算。
5. **没有版本概念。** 旧版制度和新版制度在向量空间里长得几乎一样。

### 3.3 系统层面已排查并修复的问题（已实测）

在做技术可行性验证时，发现了一个会直接导致 Agent 方案"根本跑不起来"的基础设施问题，目前已修复。

**问题**：公司部署的大模型服务（vLLM 0.9.2）未启用函数调用的工具解析器，导致 `tool_choice: "auto"` 请求直接返回 HTTP 400：

```
"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set
```

**影响面**：这不是"效果差"，而是**框架层面直接报错**。OpenAI SDK、LangChain 的 `bind_tools()`、LlamaIndex 的 FunctionAgent 默认都发送 `auto`，全部会崩。它会直接阻断 Agent 化改造。

**修复**：服务端启动参数增加

```
--enable-auto-tool-choice --tool-call-parser hermes
```

**结论**：这是部署配置问题，不是模型能力问题。Qwen3-32B 本身的函数调用能力良好（详见附录 A 的实测结论）。修复后 `auto` 完全可用。

## 四、解决方案

### 4.1 总体思路

用一句话概括：**从"一次检索"改为"三级递进的定位过程"。**

```
第一级：看目录 —— 我要找的内容在哪一本、哪一章？ 搜目录的时候 不是只匹配一个 还是根据向量多看几个目录的内容，再根据这个内容来看后面的东西。
第二级：看摘要 —— 这一章里哪几条相关？
第三级：读原文 —— 取回条款原文，逐字确认
```

对应到工程实现，是三个层次的建设：

```
文档层  → 结构感知的索引（保住条款完整性）
检索层  → 混合检索 + 精排（提供稳定候选）
路由层  → 知识目录 + 渐进式披露（提供精确导航）
编排层  → Agent 多轮闭环（允许"搜一次不够再搜一次"）
```

**核心变化**：把原来"必须一次搜对"的压力，分摊到一个可分步纠错的流程里。搜错了还有下一轮，这是 Agent 化最本质的收益。

### 4.2 文档层：结构感知索引

**目标是让切分单位从"字数"变成"条款"。**

- **按条款切分。** 以"第 X 条"为原子单位。条款过长（建议阈值 500 字）时，再按"款/项"（（一）（二）、1. 2.）切分子块，但**保留该条款全文作为父块**。
- **给每块打上完整路径（breadcrumb）。** 检索时返回的文本前面必须带：
  ```
  《员工手册》> 第三章 休假管理 > 第12条 年休假
  ```
  这一条改动成本极低，但对召回质量的提升经常被低估——它把标题层的语义直接注入了正文块。
- **补齐元数据。** 每块必须带：文件标题、章节路径、条款号、**生效日期**、**废止日期**、**适用范围**（部门/地区/员工类型）。前三个用于检索，后三个用于**过滤**——这是解决"检索到已废止制度"的唯一办法。
- **保留原文。** 索引里存的是原文副本，不是摘要。摘要只用于导航，不能用于作答。

如何构建这个目录， 用大模型来构建。

### 4.3 检索层：混合检索 + 精排

**目标是在不依赖大模型的前提下，先把候选范围收窄到可接受的程度。**

- **BM25 与向量并行，结果融合。** 这是本方案里性价比最高的一条。BM25 对条款号、金额、专有名词、制度名称的精确匹配能力，恰好补上向量的短板；而向量负责语义泛化。两者缺一不可，**不要用向量替掉 BM25**。
- **加精排（rerank）。** 检索召回 20~50 条候选，用 reranker（如 bge-reranker 系列）重排后取前 5。多召回、精排序，比"直接取 top-5"稳得多。
- **small-to-big（子块检索、父块返回）。** 用小粒度子块做检索匹配，命中后返回**完整条款原文**给模型。这解决了"检索精度"和"上下文完整性"的矛盾。
- **查询改写。** 在检索前用大模型把口语化提问改写成制度术语，并生成 2~3 个不同角度的子查询并行检索。同义词词典（请假→休假、年假→带薪年休假、开除→解除劳动合同）作为低成本补充。

> **建议的起始参数**（需用评测集调优，不要直接当结论）：
> 子块 200~400 字 / 父块为条款全文 / 检索召回 20~50 条 / rerank 后取 5 条

### 4.4 路由层：知识目录 + 渐进式披露

**这是本方案区别于常规 RAG 优化的核心，也是解决"模糊提问"的关键。**

**离线阶段：用大模型把制度库编译成一棵目录树。**

```json
{
  "node": "《员工手册》",
  "summary": "覆盖员工入职、考勤、休假、薪酬、奖惩、离职等全流程规定",
  "keywords": ["员工手册", "入职", "离职", "考勤", "休假"],
  "children": [
    {
      "node": "第三章 休假管理",
      "summary": "规定各类假期的类型、天数、申请流程与审批权限",
      "keywords": ["年休假", "病假", "事假", "婚假", "产假"],
      "clauses": ["第11条", "第12条", "第13条", "第14条"]
    }
  ]
}
```

**必须施加两条硬约束，防止大模型幻觉：**

1. `clauses` 字段只能填**真实存在的条款编号**，生成后要与索引做一次校验，不存在的编号一律剔除。
2. 目录树生成是**离线一次性的**，产物落库可人工复核。制度更新时增量重建对应子树，不重跑全量。

**在线阶段：三级披露。**

| 级别 | 提供给模型的内容 | 模型的动作 |
|---|---|---|
| 一级 | 目录树顶层（文件 + 章） | 判断该进哪个文件、哪一章 |
| 二级 | 选中章节下的条款标题 + 摘要 + 条款号 | 判断该读哪几条原文 |
| 三级 | 条款原文（完整） | 基于原文作答 |

**关键设计：目录导航与向量检索并行，结果融合，而不是二选一。**

用目录导航取代检索是个常见的错误做法——它是单点失败，目录第一层选错，后面全错且无法挽回；而向量检索至少是"排序不理想但答案还在候选里"。两者是互补关系：目录擅长处理"我不知道该找什么"的模糊查询，检索擅长处理"我知道大概问什么"的具体查询。

### 4.5 编排层：Agent 多轮闭环

**目标是让系统允许"搜一次不够，再搜一次"。**

- **把检索能力工具化，交给大模型调用。** 建议的工具集：
  - `list_catalog(level, parent)` —— 查看目录某一层
  - `search_policy(query, filters)` —— 混合检索，返回条款列表（标题+摘要+条款号）
  - `read_clause(doc, clause_no)` —— 按条款号读取原文
- **允许纠错迭代。** 模型首轮检索后自行判断："证据够不够？不够就换个说法再搜 / 沿交叉引用再查。" 这直接对应 2.2 里的"跨条款依赖"问题。
- **利用交叉引用。** 制度文本里"参见第 X 条""依照第 X 条规定"密度很高，这是被普遍低估的高价值线索。检索到含引用的条款后，顺手把被引用条款也取回来。
- **必须设收敛上限。** 建议最多 3~5 轮，或累计工具调用达到阈值后强制作答。否则会出现两个问题：延迟不可控；模型在信息不足时反复空转。
- **兜底策略。** 达到轮次上限仍未定位到原文时，明确回答"未在制度库中找到明确规定"，**绝不能凭记忆编造条款**。

### 4.6 生成层：答案必须落到原文

- **强制引用条款编号。** 每条结论后面标注来源，如"（《员工手册》第 12 条）"。这既是给用户的信任凭据，也是给评测的抓手。
- **明确区分"摘要"与"原文"。** 实测发现（见附录 A 第 3 条），模型存在用检索摘要作答、而非原文作答的倾向。对策：要求凡引用具体内容必须经过 `read_clause`；或者让 `search_policy` 直接返回原文而非摘要。
- **锁定助手身份。** 实测发现模型在自由发挥时会暴露底层模型身份（问"你是谁"会回答"我是通义千问"）。系统提示必须硬约束："你是公司规章制度助手，只回答制度相关问题。"
- **无据不答。** 检索不到明确规定时，回答"未找到相关规定，建议咨询 HR"，并给出咨询入口。

### 4.7 上下文预算（硬约束）

当前部署的模型上下文上限为 **32000 tokens**，这是个必须精打细算的硬约束。

`【待确认】：是否有计划升级到更大上下文的模型`

在 32K 内的建议预算分配：

| 用途 | 预算 |
|---|---|
| 系统提示（身份 + 规则 + 格式） | ~1K |
| 目录树（按层加载，不一次给全树） | ~3K |
| 检索结果（条款原文，每次限长） | ~8K |
| 对话历史（超过 3 轮做摘要压缩） | ~6K |
| 输出预留 | ~2K |
| 余量 | ~12K |

配套措施：目录树按需分层加载；检索结果每次最多返回 3~5 条原文；多轮历史滚动摘要。

## 五、分阶段实施路线

**不要一次性全量改造。** 按下面的顺序推进，每个阶段都有独立的验收标准，能随时停下来评估收益。

### 阶段 0：建立评测集（1~2 周）

**这是全部工作的前提。**

- 收集 200~300 条**真实用户提问**（不要自己编，编出来的问题分布是偏的）
- 人工标注每条问题应命中的条款 ID
- 建立分桶标签：术语类 / 精确条款类 / 模糊场景类 / 跨条款类
- 指标：条款级 `Recall@5`、`Recall@10`、端到端答案准确率


### 阶段 1：文档层 + 检索层改造（1~2 周）

- 结构感知切分 + breadcrumb + 元数据补齐
- BM25 与向量混合检索（搜）
- reranker 精排
- small-to-big 父块返回


### 阶段 2：目录树 + 渐进式披露（2~3 周）

- 离线生成知识目录树，含幻觉校验
- 实现三级披露流程
- 目录导航与向量检索并行融合

**验收**：模糊场景类和跨条款类的召回率提升；目录导航在"提问不含明确关键词"的用例上明显优于纯检索。

### 阶段 3：Agent 编排 + 生成约束（2 周）

- 工具化 + 多轮闭环 + 收敛控制
- 交叉引用扩展
- 引用格式强制、身份锁定、无据不答

**验收**：端到端答案准确率达标；平均轮次与延迟在可接受范围。

## 六、技术可行性验证

方案依赖的核心能力已在实际部署的模型服务上完成验证，结论如下（完整记录见附录 B）。

**服务实况**

- 端点：`http://172.16.120.211:31210/v1`
- 模型：`qwen`（实际为 `Qwen/Qwen3-32B`）
- 服务框架：vLLM 0.9.2
- 上下文上限：32,000 tokens
- 推理模式：thinking 关闭，空载延迟 0.18s

**函数调用能力**

| 能力项 | 结果 |
|---|---|
| 基础对话 | 正常 |
| `tool_choice: "auto"`（修复配置后） | 正常 |
| `tool_choice: "required"` | 正常 |
| 指定具体函数名 | 正常 |
| 流式 tool_calls（SSE） | 正常 |
| 并行 tool_calls | 正常 |
| 多轮 tool 结果回填 | 正常 |
| `response_format: json_schema` | 正常，严格遵循 schema |

**自主决策质量（这是 Agent 化的关键前提）**

- 应调工具时正确调用：3/3 正确（精确条款→读原文、模糊场景→语义检索、业务问题→检索）
- 不应调工具时正确克制：3/3 正确（问候、致谢、算术均未触发工具调用）
- 多轮链式闭环：`检索 → 读原文 → 作答` 三步收敛，正确引用条款编号

**已知限制（需在工程实现中规避）**

1. **`parallel_tool_calls: false` 无效。** 实测传 `false` 仍返回 2 个 tool_calls。**编排代码必须遍历整个 tool_calls 数组，不能只取 `[0]`**，否则会静默丢失调用。
2. **模型会暴露底层身份。** 需在系统提示中硬约束。
3. **模型可能用摘要冒充原文作答。** 需在提示中强制"引用内容必须经 read_clause 确认"。

## 附录 A：技术验证的关键发现

1. **函数调用问题是部署配置问题，不是模型能力问题。** vLLM 未加 `--enable-auto-tool-choice --tool-call-parser hermes` 时，`auto` 直接返回 HTTP 400，会阻断所有主流 Agent 框架。加入后完全可用。**这是 Agent 化改造的前置条件，必须确保生产环境已配置。**

2. **`parallel_tool_calls: false` 在 vLLM 0.9.2 上被静默忽略。** 三态对比（不传 / true / false）均返回 2 个 tool_calls。编排代码必须按数组处理。

3. **模型存在"摘要冒充原文"的倾向。** 多轮测试中，搜索结果返回 3 条摘要，模型只读取了其中 1 条原文，却在最终回答里引用了未读取的那条的内容。需要在提示层强制约束。

4. **模型身份暴露。** 无系统提示约束时，问"你是谁"会答"我是来自阿里云的大规模语言模型，我叫通义千问"，且语气偏随意（带 emoji）。生产环境必须锁定身份与语气。

5. **执行环境注意**：开发机上 `bash` 指向 WSL，不识别 Windows 路径，需显式调用 `C:\Program Files\Git\bin\bash.exe`。
